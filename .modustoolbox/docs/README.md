## MCU Features at a high level

TRAVEO™ T2G (device prefix `CYT*`) covers two distinct PDL sub-families — verify which one applies to CYT2BL3CAS before writing peripheral code:

- **`cat1a` (one Cortex®-M4 application core)** — e.g. `CYT2Bx` parts, boards like `KIT_T2G-B-E_LITE`. A device may also have a Cortex®-M0+ system core; the B-E BSP declares both `CORE_NAME_CM0P_0` and `CORE_NAME_CM4_0` and includes a `CM0P_SLEEP` image. Only one HAL package exists for cat1a (`mtb-hal-cat1`), so it uses the `cyhal_*` HAL.
- **`cat1c` (multi-core)** — Arm® Cortex®-M7 application core(s) plus a Cortex®-M0+ system/startup core (e.g. `CYT3Dx`, `CYT4Bx`, `CYT6Bx` parts, boards like `KIT_T2G_C-2D-4M_LITE`, `KIT_T2G-B-H_LITE`, `KIT_T2G_B-H-16M_LITE`). Some `cat1c` parts have a single CM7 core, others have two or four CM7 cores — see the multi-core notes below if this project has more than one CM7 project. **HAL convention is not fixed for `cat1c`**: newer/per-device HAL packages (`mtb-hal-t2g<name>`) use `mtb_hal_*`, but some code examples still depend on the generic `mtb-hal-cat1` package and use `cyhal_*` instead — always check the project's actual HAL dependency (`libs/*.mtb` or Makefile `COMPONENTS`) rather than assuming from the device sub-family alone.

Common automotive-focused peripherals across the family: CAN FD, TCPWM (timer/counter/PWM), SCB-based serial (I2C/SPI/UART), SMIF (QSPI/OSPI flash and PSRAM), DMA (P-DMA and, on `cat1c` parts, AXI-DMA), and ECC fault detection on flash/RAM/DMA.

## API Guidance

- Confirm the project's actual HAL dependency (`libs/*.mtb`, or `mtb_shared/` folder name, or Makefile `COMPONENTS`) before assuming a HAL convention — mixing `cyhal_*` and `mtb_hal_*` calls in the same project will not compile. `cat1a` is always `cyhal_*`; `cat1c` can be either, depending on whether the project uses the generic `mtb-hal-cat1` package or a per-device `mtb-hal-t2g<name>` package.
- PDL (`Cy_*`) headers under `mtb_shared/mtb-pdl-cat1/` (and `mtb_shared/mtb-dsl-<device>/` for device-specific personalities) are authoritative for exact API availability.

## Skill and Tool Reference

For build commands, library management, and GUI tools, use the deployed skill tools — **never invoke `make` directly**:

| Task | Tool |
|------|------|
| Build, clean, program, getlibs | `python .github/skills/mtb-tools/scripts/run_make.py --args <target>` |
| Launch a GUI configurator | `python .github/skills/mtb-tools/scripts/run_tool.py <tool>` |

`mtb-tools` is always deployed, so the paths above are safe to use directly. For **every other** capability, **discover skills dynamically** — scan `.github/skills/*/SKILL.md` frontmatter for the one matching your task and confirm the file exists before relying on it. Deployed skills vary by board and extension version, so this document deliberately does not list them.
